# Local demo seeders verification report

Verified on 8 October 2026. This records the reviewer-friendly demo seeders requested after issue #6; [README setup and credentials](../README.md#demo-data-and-login) is the user guide. The earlier [issue #6 report](issue-6-validation.md) records the event model milestone before these additions.

## Changes and assumptions

`database/seeders/DatabaseSeeder.php` delegates to `DemoSeeder.php`. The demo seeder accepts only `local`/`testing` before database work, including direct class invocation. It explicitly hashes new account passwords and creates one customer, one organiser, three active catalogue types and six sample events. No admin, token, reservation or waitlist is seeded. New occupancy counters are zero.

The complete fixture set is created in one transaction. Stable customer/owner and type locking plus three deadlock attempts support repeated runs. Existing rows are left intact. Wrong-role email collisions, new events requiring inactive types and failed writes abort the whole operation.

Fixture identities are the two demo email addresses, three type slugs and owner/event titles. Renaming or deleting an identity can cause its original sample to be recreated. Existing schedules remain unchanged as time passes, so an upcoming sample eventually becomes past. A deliberate `migrate:fresh --seed` recreates a fresh demo and deletes existing local records; plain `db:seed` preserves them.

No schema, API, model guard, dependency or booking workflow was changed for this addition. The earlier event/authentication implementation and the personal `.gitignore` edit remain intact. The README provides first-run migration/seeding, local credentials, sample descriptions, login and reset commands. `why.md` includes two brief interview talking points about seeders.

## Findings and role outcomes

Developer-found integrity defect: an Eloquent creating/saving listener can return `false` instead of throwing, which could otherwise leave a partial fixture set committed. **Fixed** by checking each user/type/event save and throwing on refusal. All three veto paths passed rollback regressions.

Developer implementation is complete. Focused and full tester acceptance passed with no unresolved implementation finding. The security reviewer rechecked the save-refusal fix and reported no new actionable or unresolved security/data-integrity finding. The reviewer used read-only source/framework review and no-database probes; Docker tests are the tester's separate execution. The coordinator applied the non-destructive seed and replay to the normal app only after those checks passed.

The coordinator exercised the manual seed/replay, row-count/preservation and standalone login/current-user/logout checks. The tester's environment/collision/retirement/failure scenarios ran only in the isolated test database. A browser walkthrough and destructive reset were not performed.
